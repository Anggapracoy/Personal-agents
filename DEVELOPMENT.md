# Development guide

## Architecture

Dash has two layers in this repository:

- The Next.js application contains the product UI, authentication, integrations, decision feed, and agent behavior.
- `ios/` contains the native SwiftUI iPhone shell. It owns native navigation, authentication handoff, Apple Calendar access, haptics, downloads, sharing, Live Activities, and other iOS-only behavior while displaying the hosted product.

Keep shared product behavior in the web application unless it genuinely requires an Apple framework or native bridge. Keep native-only behavior in `ios/` and preserve the bridge contract in `/api/mobile/config`.

## Local development

1. Copy `.env.example` to `.env.local` and configure the services being exercised.
2. Run `pnpm install`.
3. Run `pnpm dev` for the web application at `http://localhost:3000`.
4. For iPhone work, open `ios/DecisionFeed.xcodeproj`, select the `DecisionFeed` scheme and an iPhone simulator, then run the Debug configuration. Debug loads the local web server; Release loads the production Vercel URL.

## Google OAuth branding

Create Google OAuth clients in your own Google Cloud project. Set the public application origin and optional Search Console verification token as described in `docs/INSTALLATION_CONFIG.md`.

Native Google sign-in and connection authorization use the initiating application origin. Register `/api/auth/callback/google` and `/api/connections/google/callback` for each origin you operate. Connection completion remains bound to the initiating account, operation, and app origin through encrypted state; do not replace those checks with a cross-domain allowlist.

## Google push discovery

Automatic discovery is event-driven, not periodic inbox polling:

- Gmail publishes mailbox changes to Google Cloud Pub/Sub. The push subscription calls `/api/webhooks/google/gmail?token=<GOOGLE_GMAIL_WEBHOOK_SECRET>`.
- Google Calendar calls `/api/webhooks/google/calendar` directly for changes to each connected account's primary calendar.
- Both receivers dispatch the account-scoped `decision-feed/google.source.changed` Inngest event. One job runs at a time per Google connection.
- Gmail jobs use its persisted history cursor and retrieve only changed message IDs. Calendar jobs refresh the bounded upcoming-event window and reconcile conflict cards.
- `google_source_watches`, `discovery_scan_states`, and `workspace_states` hold watch metadata, Gmail cursors/evidence, and user-visible results in Postgres.
- `/api/cron/google-watches` runs daily from `vercel.json` to create and renew expiring watches. New OAuth connections also enroll immediately.

Before enabling this in an environment, apply migration `0008_google_push_watches.sql`, set all `GOOGLE_*` push variables from `.env.example`, configure Inngest, create the Pub/Sub topic/subscription, and grant the Gmail API publisher service account access to the topic. Keep the manual Scan control as a fallback because provider notifications may be delayed or dropped.

## Branch workflow

Choose development and production branches for your own repository. This source distribution does not include a Git remote or a connected hosting project. Preserve local work and review the full diff before publishing.

## Remote decision notifications

Remote notifications are sent by the cloud discovery workers, so they continue to work when the iPhone app is closed:

- The iOS app registers its APNs device token through `/api/mobile/push-tokens` after authentication and removes it during sign out.
- Newly persisted Gmail or Google Calendar decision cards create idempotent rows in `push_notification_jobs`. Morning suggestions also enqueue one conversation notification each, in the same transaction that publishes them to Home and completes their daily occurrence; retries cannot duplicate either.
- Delivery is attempted immediately and retried by the `deliver-decision-push-notifications` Inngest function.
- Invalid or unregistered APNs tokens are disabled automatically.

Before enabling notifications in an environment, apply migration `0010_remote_push_notifications.sql` and configure `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY_BASE64`, and `APNS_BUNDLE_ID`. The main app identifier and App Store provisioning profile must include the Push Notifications capability. Debug builds use the APNs sandbox; TestFlight and App Store builds use production APNs.

## Notification replies

Conversation pushes carry the `conversation.reply` category and an account fingerprint. iOS registers a `UNTextInputNotificationAction` at launch and handles its response in the background, awaiting the authenticated `/api/mobile/notification-reply` receipt before completing the system callback. The native shell saves its verified session cookie in a device-only Keychain entry after authentication, bounded by the session expiry and tied to the origin/account fingerprint. Background replies use that entry without starting WebKit; explicit sign-out clears it and fences in-flight session snapshots. WebKit cookies remain a fallback. The endpoint verifies ownership, atomically accepts or deduplicates the reply, and dispatches with a stable event ID. Unstarted suggestions resolve their context from the signed-in user's saved workspace; existing conversations retain their history and approval rules. Failed sends retain their receipt ID in a local notification with Try Again and Open Chat. No schema migration is required.

Apple references: [text input actions](https://developer.apple.com/documentation/usernotifications/untextinputnotificationaction), [registering categories and APNs payloads](https://developer.apple.com/documentation/usernotifications/declaring-your-actionable-notification-types), and [background response handling](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions).

## Release workflow

For main-agent model, reasoning-effort, prompt or browser-performance comparisons,
reuse [the fixed benchmark suite](docs/MAIN_AGENT_BENCHMARKS.md). Keep its task
fixtures stable and report correctness alongside speed, cost and tool calls.

After completing a request, keep every change local and wait for an explicit user instruction before committing, pushing, merging, deploying, or starting TestFlight work. Do not infer release authorization from the request being complete, from earlier release instructions, or from changes originating in another task or chat.

Before committing or pushing, review the intended changes and preserve unrelated local work.

For an authorized deployment, use your own Git remote, configured production branch and hosting project. Configure the hosting environment from `.env.example` and `docs/INSTALLATION_CONFIG.md`; no original hosted-service account is included.

1. Commit and push the intended changes through your repository's review process. Verify required checks and the resulting deployment revision.
2. When the change affects the native binary, archive with your own Apple identifiers and signing team, increment the build number, upload to your App Store Connect app and assign it to your configured testing groups. Verify processing and review status.

If your production branch automatically deploys, verify that deployment rather than triggering a duplicate.

Web-only changes arrive in the existing iPhone shell from the hosted URL and do not require a new TestFlight build. A new TestFlight upload is required whenever the installed native binary changes.

After publishing, verify:

- Your configured production branch contains the intended commit.
- Your hosting provider deployed that commit and the configured production URL responds.
- The **Register Inngest after production deployment** workflow runs only when the repository variable `APP_ORIGIN` is configured. Set it to your production HTTPS origin. You can also run `pnpm inngest:sync https://your-deployment.example` after the deployment is ready and verify success.
- If uploaded, App Store Connect/TestFlight shows the new build in your configured internal and external groups, and the external group lists it as the newest build with a `Testing` or review status.

Never report a release as complete based only on a successful local build or Git push; verify each applicable destination.

The final deployment confirmation must include a complete, plain-language list of everything changed in that release, including work from other tasks or chats. Derive the list from the full diff and commits since the previously deployed revision, not just the latest request or commit. Group related edits for readability, but cover every shipped feature, fix, UI adjustment, configuration change, and documentation update. Include the deployed commit, verification results, and applicable TestFlight build/status; clearly identify anything still pending or not deployed.

## Reminders and recurring work

The agent saves natural-language requests through `schedule_create`, finds them with `schedule_list`, and changes/pauses/resumes/cancels them with `schedule_update`. `reminder` delivers the saved message without a model call; `task` runs the agent and reports every occurrence; `check` compares fresh evidence with its persisted observations and calls `report_check` to decide whether to notify. An automatic task or check can use `report_check` with `completed: true` when fresh evidence satisfies its user-authorized finite objective or stopping condition. Successful finalization atomically completes only its own unchanged, active schedule, clears the next run, and sends the final notification once. Failures, cancellations, and stale occurrences cannot complete a newer schedule; ongoing tasks and watches use `completed: false`. Automatic occurrences cannot use `schedule_update`; `report_check` is the scoped completion path for both kinds. All deliveries use the original conversation and its existing notification deep link. Icons are unchanged.

Apply `db/migrations/0016_scheduled_tasks.sql` before running this version. Configure `DATABASE_URL`, `INNGEST_EVENT_KEY`, and the existing Inngest signing/serving configuration; sync `/api/inngest` so `dispatch-due-schedules` and `run-scheduled-occurrence` are registered. Production functions are registered after a successful Vercel production deployment by `.github/workflows/sync-inngest.yml`; interactive requests never wait for registration. APNs uses the existing configuration above; without notification permission, delivered messages remain in the conversation. Schedules are refused when durable storage or the background event service is unavailable; no in-process timer pretends to be a saved reminder.

A minute-level dispatcher persists occurrences before sending events. Occurrence identity, row locks, and the durable outbox prevent duplicate delivery after retries. A busy conversation defers agent work; a plain reminder can still arrive. Missed recurring occurrences coalesce into one, then continue at the next future time. Five-field cron recurrences use the saved IANA timezone (including DST); elapsed intervals retain their original anchor. Edits invalidate queued work. Work already running keeps its captured instructions. Paused approvals hold that occurrence until the user answers; a normal chat reply can supersede it. Cancelling a running scheduled task also pauses its future schedule.

Quiet checks retain their observation and action audit without adding a routine chat reply or push. A check that cannot complete must report that failure, not claim the state is unchanged. Action receipts have an occurrence scope so retries reuse a receipt while the next scheduled occurrence can intentionally perform new work, with existing approval rules still in force.

Run `pnpm test` and `pnpm lint`. For real PostgreSQL delivery/race tests, set `SCHEDULE_TEST_DATABASE_URL` to a disposable local database and run `node --conditions=react-server --import tsx --test tests/schedules.integration.test.ts`. The test creates and removes its own schema and never reads `DATABASE_URL`.

Manual conversation naming follows Kodo’s `suggest-title` pattern: the client starts an independent `POST /api/runs/[id]/suggest-title` after run creation. The authenticated endpoint reads the stored first request and uses `gpt-6-luna` with structured output, a six-second timeout and one timeout retry. A conditional store update writes title/category only while the original title still matches and no generated identity exists. It preserves execution state and metadata, and naming failure leaves the existing title usable. Plain manual chats opt in at creation; attachment-intake and proactive titles are preserved. Workspace reads/writes reconcile cached titles and categories against generated run identity, so reopening or a stale client save cannot restore the original placeholder. No migration is required.

Secure browser typing is one agent-selected value into one exact observed field. Saved login/card filling validates and focuses that selected field atomically; secret question answers still require an explicit click and retained focus. `browser_fill_login` and `browser_fill_card` require an exact `ref` and explicit `field`; `browser_fill_question_answer` also requires the target to be focused. The controller validates the target before unlocking and again before typing, never discovers counterpart fields or clicks Next/Continue/submit. Saved login/card filling may focus only the exact selected field; question-answer filling never moves focus. Secret values stay encrypted outside the browser controller and are redacted before typing begins. A phone unlock may be reused for ten minutes on the same HTTPS origin, browser generation, and tab, with a separate action receipt per typed field; reuse never extends the original approval lifetime. Card CVC is included in that release when the agent requests it. Field verification covers only the value just typed. The agent remains responsible for choosing and completing all fields and subsequent actions. Run `pnpm smoke:e2b-secure-typing` to exercise explicit click/type login and hosted card flows with test values.

The main agent loop alone decides whether to ask for missing details, continue research, or finish a reply. Do not add auxiliary LLM classifiers, reply reviewers, or completion-verification calls around that loop. Guidance to check connected context and the vault belongs in the main prompt and tool descriptions.

The main agent answers ordinary questions and simple confirmations directly. It uses `present_result` only when the app needs structured data beyond the reply, such as selectable options, evidenced savings, or a substantive task outcome with verification/external-change fields. The runtime sanitizes result formatting but does not reject or rewrite outcomes using the original card action type, keyword matches, or historical tool counts. Plain-prose fallback results make no claim of verified work or external changes. Tool authorization and pause handling remain enforced at execution.

### Agent context compaction

OpenAI agent turns enable native Responses API compaction at 850,000 tokens for `gpt-6.1-sol` (200,000 for other OpenAI models) with `store: true` on the HTTP request, allowing later inspection of Responses in OpenAI logs using the response IDs recorded in run metadata. `lib/harness/stored-openai.ts` separates persistence from replay: the SDK serializes full inline history using its non-stored conversion, then the transport sets `store: true`. This preserves encrypted compaction and reasoning instead of referencing potentially unstored or expired server items. Before each model step, `lib/harness/context-compaction.ts` selects the latest complete checkpoint and newer messages; if trimming would separate a tool result from its call, it leaves that request intact for server-side compaction. Instructions and current authorization context are supplied on every step.

The durable message and action history is never trimmed. Commentary saved early has an internal reference at its original provider position in every step, so follow-ups and restarts preserve reasoning and checkpoint ordering without duplicate chat bubbles. Legacy standalone commentary replays as inline text without its dependent provider item ID; saved messages and encrypted reasoning are preserved. Anthropic replay uses the full history with OpenAI checkpoints removed. No database migration or native build is required.

Run `node --conditions=react-server --import tsx --test tests/context-compaction.test.mjs tests/main-agent-commentary.test.mjs` for the OpenAI adapter, encrypted checkpoint replay, tool continuation, pause/resume, and transcript regression checks.

### Automatic task waits

Apply `db/migrations/0017_agent_pauses.sql` before running this version and sync `/api/inngest` to register `dispatch-automatic-waits`, `check-automatic-wait-event`, and `resume-automatic-wait`. The `pause` tool supports elapsed hours/minutes or a specific Gmail reply / newly created primary-calendar event. Timed waits are dispatched on the minute sweep (up to roughly one minute after the requested duration); event notifications are supplemented by minute reconciliation. No model or sandbox stays running during a wait. Reconnect/access failures resume the conversation with the real blocker. New user replies and cancellation invalidate the saved wait. A pending wait becomes eligible only after the agent turn has checkpointed.

Run `SCHEDULE_TEST_DATABASE_URL=<disposable PostgreSQL URL> pnpm test` to include the pause and schedule race tests; this variable must point to a test database, never production.

### Conversation organization

`GET/PATCH /api/conversations` saves per-account pin, custom title, and archive settings under `workspace_states.preferences_json.conversations`. No migration is required. Menu mutations lock the owner's workspace row, validate ownership, preserve other settings, and increment the workspace version. Ordinary workspace writes preserve the saved conversation settings even from older clients. Stable conversation keys follow the decision through execution and completion; explicit titles take precedence over generated titles in Home and chat headers. Archive retains the conversation and does not cancel its work. The Archived view supports restoring it.

The native shell uses `UIContextMenuInteraction` with visible Home row bounds published over the trusted bridge. iOS provides the menu material and interaction; Rename uses a system text-field alert. The preview fixture uses isolated local storage, while authenticated use requires successful durable API writes. Run the conversation-settings integration tests with `SCHEDULE_TEST_DATABASE_URL` pointing to a disposable local PostgreSQL database.


### Harness latency and local end-to-end benchmarks

Set `HARNESS_TIMING=1` when diagnosing latency. Message requests and agent turns log `[harness-timing]` JSON with operation names, wall-clock start, relative start times, and durations. Store operations and model requests are measured without logging arguments, message bodies, tool results, or credentials. Spans can overlap (for example model headers are inside the model request); do not add overlapping spans as if they were sequential. Normal operation leaves this flag off.

New-chat POST requests also persist a `create` timing trace, starting before body parsing and associated with the run ID immediately after creation. It covers parsing, authentication, request quota checks, parallel settings/profile reads, run and attachment storage, Google credential attachment, Inngest dispatch, snapshot loading, and response serialization. Failures after creation retain the trace; rejected requests that never create a run have no database diagnostic row. Database timing persistence does not require `HARNESS_TIMING=1`; that flag only adds console output. These server timestamps do not measure device-to-server transit or screen rendering.

Streamed narration saves its first delta immediately, batches subsequent deltas for up to 100 ms, and drains before completion, pauses, and error handling. The full transcript and final result are still durable. Independent historical reads are reused within a turn; steering and authorization checks remain live.

The HTTP Inngest client uses a 270-second checkpoint runtime beneath the endpoint's 300-second limit, with every step checkpointed. This avoids the SDK's short default HTTP runtime splitting later steps into new invocations; it does not remove initial cloud queue or cold-start latency.

Interactive chat starts (including the share sheet), replies, notification replies, approval/sign-in resumes, and Apple-action continuations use the Inngest v2 Invoke Function API for `decision-feed-agent/run-decision-agent`. The existing environment signing key authenticates these requests. Background events, schedules, and stale-worker recovery retain event dispatch. Preview environments, explicit environment overrides, and custom/development endpoints retain SDK event routing. The SDK also infers a branch name on Vercel production; that inferred branch is allowed to use the production signing key for direct invocation. Set `INNGEST_FAST_INVOKE=0` to disable direct invocation.

An invocation retries at most once with the same idempotency key and a three-second timeout per attempt. Explicit authentication, missing-function, or API-rate-limit rejections can fall back to events only if no earlier attempt was ambiguous. A lost response may already have started work: after two uncertain attempts the chat stays active, with a server warning, and existing five-minute stale-worker recovery remains available. Do not mark that chat failed or immediately dispatch a second event. Caller-supplied notification and Apple-result IDs remain stable across retries. Ordinary chat POST retries still follow the existing message acceptance semantics.

Cancellation uses `cancelOn.if` comparisons for agent runs, phone monitors, and manual scans. The deprecated `match` option accepts only a property path, not a comparison. The main agent currently retains its one-second checkpoint window, which forces follow-up work onto another invocation after longer agent steps. A local SDK experiment confirms that a larger checkpoint window can execute a short follow-up in the same invocation, while `step.sleep()` still returns control to Inngest. Raising the window is a separate pending optimization; validate execution-slice and host-deadline behavior before changing it. Keep every step checkpointed (`bufferedSteps: 1`). `worker` diagnostics now separate model loading from agent execution; `context.load` measures parallel settings/profile reads. Model initialization persists their combined metadata once. Production cancellation changes require the usual deployment and Inngest sync; local tests do not update registered cloud functions.

The agent execution step saves a small `followUps` plan using its final run state. New executions skip irrelevant wait, attention, scheduling, completion, and failure checks: an ordinary completed reply schedules only its completion notification, while silent/reaction replies schedule none. Relevant steps keep their original IDs and live-state guards, and all required effects remain inside durable steps. Previously saved execution results without this plan retain the entire legacy sequence so in-flight runs resume compatibly. Scheduled finalization and phone-monitor ordering remain unchanged.

For OpenAI models with explicit caching support, runtime context is tagged when constructing instructions and moved behind the conversation history at the provider boundary. Its system/developer priority and complete contents are retained; the stable policy stays first with its explicit cache breakpoint. This prevents current time, profile, receipt, or reaction-target updates from changing the prefix before saved history. Implicit caching and the 30-minute TTL remain enabled. The reordering happens on each provider request without mutating stored messages or the SDK's replay history; tool-call/result pairs, encrypted reasoning, compaction, and images keep their order. Other providers and untagged instructions retain their existing layout. Validate serialized requests with `tests/prompt-cache-layout.test.ts` and compaction/replay tests; production cache-hit and latency gains require a subsequent live run. Within an active task, OpenAI input also retains full explicit browser inspections as they age: appending a newer result must not rewrite an earlier inspection into a diff and invalidate its cached prefix. Deterministic action deltas and duplicate printed-snapshot removal remain in place. This favors prefix reuse over minimizing the text of old inspections; the durable history is unchanged.

New-chat profile/settings reads overlap the authenticated access checks; credentials are prepared alongside run creation. Text chats without uploaded files save encrypted Google credentials in the run-creation statement, avoiding a separate credential-write round trip; manual text chats also save the opening message atomically, using the same seed builder as worker-created history. Uploaded-file requests retain attachment setup before credential attachment. Credential preparation starts before worker-module preloading. Interactive preparation also opens and immediately releases up to two run-store database connections once per store instance, overlapping cold connection setup with request preparation without reserving a worker or taking an execution lock. Failed connection preparation is ignored and may be retried; ordinary database operations still connect normally. The `worker.preload` and `worker.connections` timing spans distinguish module loading and connection setup from overlapping database waits. Quota windows use one ordered database statement with the same early-stop semantics. Billing access reads policy, account period, and current usage in one query without caching limits. Worker lock acquisition can return the run row in the same statement, and Google credential reads are batched. Initial attachment loading reuses the already-read artifact list.

Completed-task output trimming is a deterministic model-input transform, not a summarization request. Successful finalization records `completedToolHistorySeq`; later replies retain that fixed boundary. Active steps, worker-slice retries, approval pauses, failures, and `needs_user` outcomes never advance it. On the next turn, browser `snapshot` fields over 2,000 characters and exact printed duplicates are replaced by an archive reference; `sandbox_run` stdout/stderr over that size keep their first 400 and last 800 characters (failure stderr stays intact). Other fields, tool-call/result pairing, user/assistant messages, and the durable originals remain unchanged. `read_tool_result` retrieves a bounded exact slice from a completed result in the same owned chat. Trimming runs once over saved history at turn entry, never over new results inside the active model loop. The first shortened request changes the cached prefix; subsequent replays use stable records.

Normal reply intake authorizes with the run row; quoted replies and waiting-state cleanup load the full snapshot only when needed. Quota acceptance follows ownership checks. Reply text, prior-result context, activity reset, and client connection metadata are committed in one row-locked transaction; an already-active chat receives durable steering instead. Credential lookup overlaps reply storage and encrypted credentials are attached in one batch before dispatch. Existing billing accounts avoid a redundant insert on every status check. No schema migration is required.

Historical browser use no longer reconnects a browser before the next model request. A turn-local wrapper resumes it once before the first actual browser operation, preserving cancellation and concurrent-call ordering. The model's context snapshot and prior-action reads also run in parallel. Complete-message display and generation behavior are unchanged. Validate reply concurrency/rollback with `REPLY_TEST_DATABASE_URL` pointing to disposable local PostgreSQL and `tests/reply-acceptance.integration.test.ts`; browser deferral is covered by `tests/deferred-browser-resume.test.ts`.

Profile and active-fact reads run concurrently with their existing owner filters and ordering. They are fetched afresh on every call. Model startup loads conversation history once after shared-file attachment setup and derives the task clock from that same history, rather than issuing an earlier duplicate read. Attachment repair and live steering/authorization checks retain their own reads; no messages, profile fields, or memory facts are removed by this optimization.

Attachment repair uses a scoped `hasMessages` existence query when only presence is needed. Startup reuses the fresh run returned by the heartbeat write and checks queued steering only when present; an unseeded first turn retains its original request before consuming queued replies. Later loop iterations reload the run. Empty steering checks avoid opening a transaction; nonempty steering still takes the row lock and rechecks before consumption. Tool guards and atomic finalization continue to catch input arriving after an empty read. The complete transcript is still loaded for the model.

Worker model loading overlaps execution-lock acquisition; capacity acquisition and the heartbeat write also run concurrently. Execution still requires capacity, and a failed heartbeat releases its acquired slot. After validating the locked run, the worker also starts read-only profile/settings preparation while capacity and heartbeat checks complete. This preparation is consumed once by the first turn; later turns and provider-fallback changes load fresh context. Runtime-result acknowledgement is merged into the initialization metadata write using a monotonic sequence watermark, preserving newer unread receipts. Google setup still validates the current connection but skips rewriting an identical access token. Prefetched context is joined with the startup history, and context metadata is saved with the turn initialization update. A single startup query loads the complete history, actions, and artifact metadata after attachment repair. Tool setup and prior-action reads overlap the initialization write; its returned metadata is merged into the startup snapshot. Google and phone initialization share that snapshot, while tool execution retains live authorization/state checks. PostgreSQL snapshots aggregate ordered actions and artifact metadata in one statement, excluding artifact bytes. Concurrent ownership checks share only an in-flight probe, with a fresh check after it settles. These changes reduce database round trips without changing the prompt contents, model, or complete-message display. Measure from message-handler entry to provider request, separately from worker-only timing; local database benchmarks with simulated latency do not establish production end-to-end latency.

Interactive create/reply handlers preload the worker during admitted request preparation. After confirmed durable dispatch, they may start the saved run in the existing HTTP function using `after` to retain its lifetime (300-second route budget). The same PostgreSQL execution lock arbitrates with the queued Inngest worker; only one executes the turn. Inngest retains retries, pause arming, and notification follow-ups, including after a local failure. A queued worker that finds the lock occupied uses its existing five-second retry, so follow-ups can trail local completion. Ambiguous admission never starts local execution. Local execution polls cancellation and rechecks before publishing messages. Diagnostics label this path `interactive_worker` so a later queued-worker retry cannot be mistaken for the request that generated the reply. Set `INTERACTIVE_LOCAL_START=0` to use only the durable worker. Background/event producers retain their existing path.

Event producers import `lib/harness/inngest-client.ts`, which contains only the Inngest client. Only `/api/inngest` imports registered functions. Model execution and discovery scans load inside their execution steps; the local dispatch fallback loads its model only when used. Keep model, browser, and discovery imports out of the event client. Browser takeover cleanup loads only when a message actually resumes a takeover. Production uses the existing Vercel HTTP handler; there is no separately hosted persistent-worker entry point.

When diagnosing startup, inspect Vercel request details (`functionStartType`, `functionColdStartDurationMs`, and the proxy/function timestamps) alongside the Inngest trace. Time between Inngest queuing a run and starting it is not proof of a Vercel cold start. Fluid compute and function regions are project settings; verify the live project before changing them.

For a full local benchmark, run a production Next.js build against a **disposable local PostgreSQL database**, a real Inngest Dev Server, and real model credentials. Use an isolated copy without `.env.local`, inject only the services needed for the test, and set `INNGEST_DEV=1`, `INNGEST_BASE_URL`, `INNGEST_EVENT_KEY=local-benchmark-only`, `DATABASE_URL`, `AUTH_SECRET`, and `HARNESS_TIMING=1`. Sync the app once before running `pnpm eval:latency --url http://127.0.0.1:3000 --fixture /absolute/path/fixture.json --output /absolute/path/results.json --count 3`. The fixture contains `request`, `title`, `category`, `metadata`, `result`, and AI SDK `messages`; `followUp` defaults to the brief Kodo question. The script signs an isolated local test session and exercises the real authenticated message route, dispatch, Inngest worker, harness, model, persistence, and SSE delivery. It refuses remote app/database targets. It never measures browser paint or reproduces Vercel cloud startup; report those limits with the results. Keep fixtures containing real conversation history private and out of Git.

### Internal phone calling

`RESIA_API_KEY` is a server-only funded Resia credential; `RESIA_CALL_AGENT_ID` selects the approved, active reusable Dash agent. Its configuration is defined in `lib/harness/resia.ts`. Keep task-specific briefs in call inputs instead of editing the agent per call. Supported outbound destinations are US/Canada. `phone_call` is registered according to the explicit calling-access policy described below, enabled for everyone by default; every execution also verifies access and conversation ownership. Existing call owners retain `phone_call_result` access after calling is disabled. No client credential, provider signup, or user billing flow is added.

Before calling, the agent verifies the destination and gathers needed information from the current conversation, Gmail and calendar, asking the user for essential missing facts and acceptable alternatives. The server injects the saved profile/custom instructions and all confirmed personal memories into the call brief. Dash's 10,000-character briefing limit is enforced without silent truncation. The caller uses relevant context only and cannot access live Dash tools. Never put passwords, authentication codes or payment credentials in the brief.

Calls use the existing external-action approval and receipt machinery. The exact agent ID, destination and brief are frozen in the action before dialing; the optional callback URL is attached only at dispatch so its token never enters action inputs or model history; the provider idempotency key is stable for the conversation, scheduled occurrence and attempt key. Retrying an uncertain response must reuse the original arguments. Results can only be read through a call receipt in the same conversation and are persisted as action evidence. The agent checks the transcript as well as the provider summary, then performs any authorized follow-up through normal tools. Recipient statements do not authorize new actions or saved memories.

An accepted call automatically creates a durable phone wait. After the agent checkpoints, `monitor-phone-call` checks the provider every 15 seconds for up to 75 minutes and resumes the original conversation when the call ends. Production can set `RESIA_CALL_ENDED_WEBHOOK_URL` to an HTTPS `/api/webhooks/resia?token=<random secret>` URL with at least 32 random characters. The callback authenticates that token and re-fetches the call with our API key before saving any result; never trust the unsigned webhook body as outcome evidence. Duplicates, early delivery and failed dispatch are recovered by polling and the durable pause outbox. Preview/local omit the callback and use polling. `initiated`, `post_processing`, and `unknown` remain pending; only `completed`, `error`, and `canceled` are terminal. Provider billing errors are handled at call creation so a depleted balance cannot block recovering an already accepted idempotent call. The model must not create a timed pause or poll in a loop. Monitoring failures resume with an explicit unknown-status error rather than claiming the call ended. Register the new monitor through the normal Inngest release sync. ### Model rate-limit recovery

Temporary provider rate limits checkpoint `modelRetryAt` in run metadata and keep the run active. The rate-limit regression replays the installed adapter's post-compaction failure shape and verifies cooldown, retained progress/secrets, and continuation.

### iCloud Mail

Apply `0034_icloud_mail.sql` before releasing this feature. iCloud Mail is independent of Sign in with Apple. ## Persistent proactive opportunities

Apply `db/migrations/0036_proactive_opportunities.sql` before deploying this version. This is additive: it creates owned opportunity, source-revision, and refresh-lease tables. `daily_proactive` is enabled for everyone by default; explicit saved disables and per-user exclusions are respected. This system and its two Inngest functions are exclusively behind that flag. Unflagged users retain the existing email path.

`dispatch-personal-opportunities` runs every 30 minutes and dispatches only enabled owners during 08:00–22:00 in their saved timezone. `check-personal-opportunities` classifies changed user-authored chats in bounded batches, preserving durable goals/plans beyond the recent-chat context. The normal morning worker refreshes the same memory and claims the same due records. Source revisions prevent unchanged conversations being reclassified. A 10-minute fenced extraction lease, 15-minute due-check claims, row revisions, owner-scoped writes, and atomic Home/notification publication prevent duplicate or stale delivery. Closing/declining or changing the flag during a run fences publication; generated suggestions alone never execute actions.

The extractor and independent review use GPT-6 Luna with medium reasoning. Both require actual user evidence; done status alone is not fulfilment. Only the outcome of a linked, verified task can close a purchase/booking goal. One-off puzzles, test forms, capability questions and logins are excluded; a purchase is not inferred to be a hobby. Explicit user-requested practical needs remain eligible, while new unsolicited opportunities focus on personal life. Active schedules and underway tasks own their work; do not create another watcher for them.

Due checks retain dated verification observations, observed public source URLs, and the next useful check time, including when zero suggestions are warranted. Future/closed leads cannot ground new offers. Repeated searches under one personal anchor do not satisfy research breadth. One refusal cools down its offer, not its entire category; repeated category feedback is shared with the morning path. Explicit “less like this” closes the lead until a newer user request. Account/data deletion removes the new memory tables' owned records. Existing chat records and explicit recurring checks are preserved.

Validate with `tests/proactive-opportunities.test.ts` (isolated PGlite, no production writes), `tests/morning-ideas.test.ts`, and the existing proactive suites. `node --env-file=.env.local --conditions=react-server --import tsx scripts/proactive-opportunity-eval.ts` runs a paid, read-only model evaluation on clearly synthetic examples, without creating runs, saving records, or notifying anyone. It checks a blocked treadmill goal, an already booked future trip, tests and one-off puzzles. Production backfill starts only after migration and deployment; no live account was backfilled during implementation.

Explicitly time-bound opportunities carry a useful-until timestamp and expire without being treated as a successful result or a negative category preference. Source/lease/revision checks also fence an account-data deletion during model work; stale cached context cannot recreate deleted memory. User-data deletion clears morning and proactive delivery ledgers as well as the new records. Publication holds a shared lock on the existing feature-policy row, serializing a flag change with its commit.

Recurring-purchase evidence uses one shared prompt rule for extraction, independent review, and morning generation/review. A narrow product pattern requires at least two independent verified completed purchases over time, with literal user requests and completion excerpts retained as provenance. Incremental classification can consult an owner-scoped recent verified-purchase comparison pool without reclassifying those historical runs. Searches, cancelled orders, receipt copies and generated offers do not qualify. Patterns stay active after an order is fulfilled; an opt-out is not overridden by buying again. This supports purchases performed in saved chat history. Automatic external-inbox receipt pattern ingestion remains separate and is not implemented by this change.

### Resolved proactive rule audit (October 5)

- Shared `opportunityTimingGuidance` distinguishes a preferred/blocked attempt window from a hard final goal deadline. Relative timing is interpreted at the authored turn's time and saved timezone. Hard expiry requires a quoted user limitation or verified fixed-occasion outcome; a mere “tonight” or “not now” does not silently cancel an unmet wish. Expiry provenance is retained in the opportunity evidence.
- Reviews classify distinct offers, unchanged duplicates, justified due-goal renewals and new routine cycles. A renewal may reference the earlier offer in `duplicateOf` when concrete new value is established. Due/open status, meaningful justification, valid comparison references and same-pass deduplication remain required. Merely rewording an unanswered offer does not qualify.
- `MORNING_OFFER_WINDOW_MS` supplies the same 72-hour maximum to model context and runtime validation. An offer cannot outlive an associated hard deadline; publication also checks that deadline at commit. This offer window is separate from a long-lived opportunity's next-check time.
- Actual authored user turns, not the original chat's source label, establish new personal intent. Nonmanual-origin chats can contribute genuine later requests. Generated openings, suggestion labels, reaction scaffolding and runtime instructions are not authored evidence. Selected labels can support a routine only alongside independent verified completed purchase evidence. The newest authored occurrence is used when a request is genuinely repeated after closure.

Useful-reply exceptions under the feature flag and receipt exclusion specifically from open-loop reply detection remain intentionally scoped policies. All new personal-opportunity processing stays behind the existing daily proactive flag; no default-user email-path rules or live account flags were changed.
